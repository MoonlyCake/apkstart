# ApkStart 重构 · 第一阶段

本阶段从上游 `a4d4a23cdd20d8943703ae172a0c8734ca23b097` 提取现有行为，在保留用户数据和既有入口的前提下逐条替换核心逻辑。不是整体切换到新运行时，也不修改发布版本号。

## 已替换的核心

- **操作队列**：从资源管理器、快捷方式和界面进来的安装及启动操作共享一条 FIFO 队列。同一应用在队首或队中时的重复启动合并；前一次失败不阻塞后续请求。界面不会把“已有安装在排队”当成安装成功。
- **启动策略**：只有同一个 PID 在观察窗口内稳定存活才报成功；超时和 ADB 断连不是闪退证据。确认进程退出才重试，不在普通启动中清数据、强停或自动授予权限。提前接窗口失败时，在进程稳定后补接；保留已有缓存恢复。需要 ARM 兼容镜像时提示原因，不在普通启动中切换或重建运行时。
- **本地状态**：`settings.json` 和 `apps.json` 路径及格式不变，保留 BOM 与未知字段。只在文件不存在时使用默认值；损坏或不可读时说明原因并停止启动，不覆盖原文件。旧设置在读取时只做内存迁移；保存使用同目录临时文件加原子替换。显式重置安卓数据前先校验清单，清理后若清单提交失败，不报告成功。

保留 `.apk` 文件关联、`--launch`、桌面/开始菜单快捷方式和窗口方式；本阶段不更改它们的接口。保留用户主动执行的安装、授权及清数据入口。

## 验证与下一步

`npm test` 运行既有套件和新核心测试，也可用 `npm run test:rewrite` 单独检查。核心使用模拟 ADB 和临时状态目录，不能替代真实 Android 启动验证。

1. **运行时归属**：按受管路径、进程身份、AVD 和 ADB 标识判定归属；未知实例不复用、不终止。先用假进程验证，再在 Windows 10/11 上与其他模拟器共存测试。
2. **安装事务**：分离拆包 staging、guest 安装、清单提交与快捷方式恢复。覆盖 split APK、磁盘不足、安装成功但清单写入失败以及中途退出。
3. **端到端验收**：分别验证冷启动/快照重启、原生/嵌入窗口、Unicode 路径、DPI、WHPX/软件回退、便携/安装/MSIX。麦克风输入与耳机播放分开验证；启动成功不代表录音已可用。
